# اتصال پذیرش واقعی فرم امداد

فرم در `/امداد-خودرو-آنلاین` و صفحه اصلی قرار دارد. وضعیت اتصال از `GET /api/service-requests` در زمان اجرا دریافت می‌شود؛ کلید و آدرس مقصد به مرورگر فرستاده نمی‌شوند.

## حالت پیش‌فرض و مرز مسئولیت

**بدون اتصال معتبر، هیچ سفارش آنلاینی ثبت نمی‌شود.** فرم خلاصه را در مرورگر برای تماس آماده می‌کند. این رفتار عمدی است و با پیام موفقیت ساختگی جایگزین نمی‌شود. دستیار هوشمند و کانال بله هم سفارش ثبت نمی‌کنند.

این مخزن دیتابیس سفارش، پنل اعزام، نقشه زنده، پرداخت یا سیستم پیامک ایجاد نکرده است. برای پذیرش واقعی، سامانه دریافت‌کننده‌ای متعلق به کسب‌وکار باید توسط مدیر سرور پیکربندی شود. سرویس باید پذیرش را واقعاً ذخیره و به اپراتور منتقل کند؛ صرف پاسخ‌دادن `accepted: true` بدون انجام آن کار درست نیست.

## تنظیم روی سرور

متغیرهای **فقط سمت سرور**:

| متغیر | کاربرد |
| --- | --- |
| `SERVICE_REQUEST_WEBHOOK_URL` | URL کامل HTTPS سامانه پذیرش؛ بدون نام کاربری/رمز داخل URL. |
| `SERVICE_REQUEST_WEBHOOK_TOKEN` | اختیاری؛ توکن محرمانه مقصد، ارسال‌شده به شکل `Authorization: Bearer …`. |

متغیرها را در محیط سرویس Node یا فایل محیطی مناسب سرور قرار دهید و همان سرویس را با محیط جدید راه‌اندازی مجدد کنید. هیچ مقدار محرمانه‌ای را در Git، گفتگو، `NEXT_PUBLIC_*` یا فایل سمت مرورگر نگذارید. بدون URL معتبر، API وضعیت غیرفعال اعلام می‌کند. تغییر این تنظیم صرفاً runtime است؛ تنظیمات عمومی آمارگیر و تأیید Search Console برخلاف آن معمولاً هنگام build خوانده می‌شوند.

## قرارداد درخواست به مقصد

درخواست HTTPS با روش `POST` و `Content-Type: application/json` ارسال می‌شود. `Idempotency-Key` برابر `requestId` است. مقصد نباید ریدایرکت بدهد. انتظار پاسخ حداکثر ۱۰ ثانیه است.

بدنه شامل این فیلدها است:

| فیلد | معنا |
| --- | --- |
| `requestId` | UUID نسخه ۴؛ برای جلوگیری از سفارش تکراری |
| `service` | شناسه خدمت از `src/content/service-options.ts` |
| `region` | تهران، کرج و حومه، گیلان، مازندران یا گلستان |
| `vehicle` | مدل و شرایط خودرو، حداکثر ۱۰۰ نویسه |
| `phone` | شماره همراه ایران، نرمال‌شده به شکل `09…` |
| `location` | نشانی و جهت حرکت، ۸ تا ۶۰۰ نویسه |
| `notes` | شرح اختیاری، حداکثر ۱۲۰۰ نویسه |
| `consent` | مقدار `true` پس از تأیید کاربر |

مقصد باید کلید تکرار را به‌صورت پایدار و اتمیک نگه دارد؛ اگر همان درخواست دوباره رسید، **همان مرجع قبلی** را بدون ایجاد سفارش دوم برگرداند. تغییر محتوای همان کلید نباید سفارش جدید ایجاد کند. API این مخزن در صورت قطع پاسخ، خودکار دوباره درخواست را ارسال نمی‌کند. مرورگر در تلاش مجدد با اطلاعات یکسان، همان کلید را نگه می‌دارد؛ پس از نوسازی صفحه چنین تضمینی وجود ندارد و تماس برای رفع ابهام مهم است.

## قرارداد تأیید

تنها پاسخ موفق HTTP از نوع JSON، با تأیید صریح زیر، پذیرفته می‌شود:

```json
{
  "accepted": true,
  "reference": "REQUEST-12345"
}
```

مرجع باید ۱ تا ۸۰ نویسه از حروف، اعداد، فاصله یا نشانه‌های `_ . / -` باشد. پاسخ HTML با وضعیت ۲۰۰، پاسخ بدون `accepted: true`، خطای مقصد یا نبود مرجع، موفقیت محسوب نمی‌شود. اندازه پاسخ نیز محدود است.

API سایت پس از تأیید، HTTP **۲۰۱** با `status: "received"` برمی‌گرداند. این پیام فقط **تحویل اطلاعات به پذیرش** است؛ نه تأیید مبلغ، زمان، پرداخت یا اعزام. تأیید نهایی باید با اپراتور انجام شود.

## خطا، امنیت و حریم خصوصی

- درخواست بدون Origin هم‌میزبان یا cross-site: **۴۰۳**؛ ورودی نامعتبر: **۴۰۰**؛ نوع محتوا نامناسب: **۴۱۵**؛ بدنه بیش از ۸KiB: **۴۱۳**.
- مقصد غیرفعال: **۵۰۳**؛ عدم تأیید تحویل: **۵۰۲**؛ تلاش بیش از حد: **۴۲۹**.
- محدودکنندهٔ درون‌حافظه‌ای: ۱۰ تلاش در ۱۰ دقیقه برای شناسه درهم‌سازی‌شده IP، حداکثر ۱۰٬۰۰۰ کلید در هر فرایند. با restart پاک می‌شود و در چند replica اشتراکی نیست.
- کانفیگ نمونه Nginx موجود، `X-Real-IP` را با IP اتصال بازنویسی می‌کند. پورت Node را مستقیم عمومی نکنید. پشت Cloudflare یا چند پراکسی، Real IP را فقط از پراکسی‌های مورداعتماد تنظیم کنید؛ در غیر این صورت همه کاربران ممکن است IP مشترک داشته باشند. برای ترافیک واقعی، محدودسازی مشترک/WAF مناسب اضافه کنید.
- اطلاعات مشتری و پاسخ مقصد در لاگ برنامه یا رویدادهای آمارگیری ثبت نمی‌شوند. فرم در URL، localStorage یا صف آفلاین ذخیره نمی‌شود. لاگ‌های پراکسی و نگهداری مقصد باید جداگانه توسط مدیر بررسی شوند.
- API و وضعیت فعال‌بودن `no-store` هستند و service worker آن‌ها را cache نمی‌کند.
- رویداد `service_request_prepared` فقط آماده‌سازی، `service_request_attempt` فقط تلاش، و `service_request_received` فقط تأیید تحویل است. فقط رویداد آخر نامزد اندازه‌گیری پذیرش است؛ حتی آن نیز فروش یا اعزام نهایی محسوب نمی‌شود.

## پیش از فعال‌سازی برای مشتری واقعی

۱. روی محیط آزمونِ خود کسب‌وکار، با داده مصنوعی و اطلاع اپراتور، پذیرش موفق و مرجع واقعی را بررسی کنید.
۲. همان شناسه را دوباره ارسال و عدم سفارش تکراری را تأیید کنید.
۳. پاسخ ۵۰۰، قطع ارتباط، تأخیر و JSON نامعتبر را امتحان کنید؛ سایت نباید آن‌ها را موفق نشان دهد.
۴. رسیدن درخواست به اپراتور و مسیر پیگیری کد را بررسی کنید.
۵. سیاست نگهداری اطلاعات، دسترسی کارکنان و درخواست حذف/اصلاح را تعیین کنید.
۶. سپس مقصد production را روی سرور فعال کنید. توکن یا URL محرمانه برای انجام این کار نباید در گفتگو ارسال شود.

آزمون‌های مخزن قرارداد انتقال را با مقصد ساختگی و رفتار UI را با mock بررسی می‌کنند؛ **اتصال واقعی کسب‌وکار در این محیط پیکربندی یا تأیید نشده است.**
